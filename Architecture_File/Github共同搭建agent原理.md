# 在 GitHub 上共同搭建 AI Banking Agent：团队协作架构教程

> 本教程依据现有架构资料 [AI_Banking_Agent_Architecture_Complete.md](./AI_Banking_Agent_Architecture_Complete.md) 的第四部分编写，面向「1 名大二 + 4 名大一」的五人团队。它将架构建议转化为角色安排、GitHub 协作方式和分阶段开发流程。若团队人数、经验或实际赛程不同，应调整工作量和节奏，但应保留接口先行、主责与备份、持续集成和业务验收等核心原则。

## 1. 协作架构的目标与设计依据

### 原理与取舍

五人团队若简单地把 Agent、Quant、Backend、Frontend、RAG 各自划给一人，表面上分工平均，实际上可能导致每个模块只有一名成员理解，系统整体仍依赖一个人整合。尤其在「一名大二、四名大一」的团队中，成员对技术和业务的熟悉程度可能不同；一开始让每个人独立设计复杂模块，容易造成接口不一致、重复学习和集成延迟。

因此，第四部分建议采用「一名技术总负责人 + 两名核心开发 + 两个可逐步升级的岗位」。技术负责人保证系统模块可以连接成完整 Agent；大一成员从清晰、可拆分、可以验证的任务开始，逐步承担更复杂的实现。此方案并不表示其他人只执行命令，而是将架构决策、具体实现和学习成长安排在同一协作过程中。

### 结果与操作

团队先以文字确认以下约定，并放入仓库的项目说明或协作文档：

- 团队人数与角色：`[成员1：大二]`、`[成员2至成员5：大一]`。
- 项目首要目标：构建 `[个人财务管理 / 其他已选业务场景]` 的可演示 AI Banking Agent。
- 第一版只聚焦 `[1-2 个完整业务旅程]`，不以功能数量作为主要进度指标。
- 所有模块按公开的接口契约协作；业务问题、金融逻辑、工具调用和测试结果必须能串成一个闭环。
- 每项关键工作同时安排 Owner 与 Shadow，避免知识只保留在一名成员手中。

## 2. 五人团队角色设置

### 原理与取舍

角色名称要对应明确的交付物，而不是听起来专业的头衔。特别是大一成员，不应仅凭“负责 Backend”或“负责 Quant”承担边界不清的工作。将复杂工作拆成可以逐步升级的任务，既能产出可集成代码，也能让成员边做边学习。技术负责人也必须避免包揽全部代码、调试、演示和材料工作，否则团队会退化为一人开发、其他人旁观。

以下分工依据参考架构第四部分的最终推荐。实际可根据能力调整，但应保留每个角色的清晰职责和协作关系。

### 结果与操作

| 成员 | 推荐角色 | 首要职责 | 可逐步承担的工作 |
|---|---|---|---|
| `[成员1：大二]` | Tech Lead / Agent Architect | 总体架构、Agent Workflow、LLM 调用、Prompt Framework、Tool Calling、状态管理、模块接口和集成 | 金融逻辑定义、Demo 主流程、系统讲解 |
| `[成员2：大一，代码能力相对较强]` | Agent / Backend Engineer | 先实现清晰的工具函数和 API，例如 `get_transactions()`、`get_account_balance()`、`calculate_budget()`、`get_user_profile()` | Tool Registry、Function Calling、FastAPI、REST API、JSON Schema、数据库和 Agent-Tool 集成 |
| `[成员3：大一]` | Financial Data & Quant Engineer | 数据清洗、交易分类、计算实现与结果可视化 | 现金流、储蓄率、支出比例、债务比率、流动性指标；再评估组合收益、波动率、Sharpe Ratio、VaR 或回撤等进阶指标 |
| `[成员4：大一]` | Frontend / Visualization | Dashboard、聊天界面、Agent 状态展示和数据可视化 | 前端 API 调用、图表、交互和结果展示 |
| `[成员5：大一，代码基础可相对薄弱]` | RAG / Research / Evaluation | 金融资料研究、知识库整理、RAG、测试问题集、结果评测与文档 | Embedding、向量数据库、检索、重排、Prompt Grounding、安全测试，逐渐成长为 AI Evaluation Engineer |

**成员1的工作边界：**成员1负责保证系统方案连贯和接口可集成，但不应独自完成前端全部代码、后端全部代码、Quant、演示材料和所有 Debug。每个模块由对应 Owner 实现，Tech Lead 通过契约、技术指导、评审和集成支持全队。

## 3. Owner + Shadow 协作制度

### 原理与取舍

如果每个模块都只有一个 Owner，开发会比较直接，但当 Owner 忙碌、缺席或更换任务时，其他成员可能无法继续维护。若每个决定都要求全体参与，讨论成本又会拖慢开发。Owner + Shadow 在责任清晰和知识共享之间折中：Owner 对模块交付负责；Shadow 参与讨论、阅读实现、协助测试或完成小改动，并能在 Owner 不在时帮助排障。

Shadow 不是旁观者，也不是额外审批层。安排该制度的目的，是让团队逐渐扩大能理解系统的人数，而不是让所有内容都经过 Tech Lead。

### 结果与操作

可以从以下安排开始，之后依实际任务调整：

| 模块 | Owner | Shadow / Reviewer |
|---|---|---|
| Agent 架构、Workflow、LLM 集成 | `[成员1]` | `[成员2]` |
| Agent 工具与 Backend API | `[成员2]` | `[成员1]` |
| 金融指标定义与 Quant 计算 | `[成员1]`负责业务/指标定义；`[成员3]`负责数据和实现 | `[成员3]`参与定义复核；`[成员1]`审查实现 |
| Frontend / Dashboard | `[成员4]` | `[成员1]`或`[成员2]` |
| RAG、Research、Evaluation | `[成员5]` | `[成员1]`或`[成员2]` |

每个 GitHub Issue 都填写 Owner、Shadow、验收条件和关联模块。Shadow 至少参与一次接口讨论、一次 PR 评审或测试验证；高风险或核心模块还应安排 Shadow 完成一个小型修复或独立复现步骤。每周由模块 Owner 用简短演示说明已完成内容、当前接口和阻塞项，让知识在团队内流动。

## 4. GitHub 仓库和日常协作流程

### 原理与取舍

GitHub 流程的目的不是增加手续，而是让成员知道当前工作、接口约定、代码变更和验证结果。Issue 用来定义一项可验收的工作；分支让实现彼此隔离；Pull Request（PR）集中代码审查和测试；合并到主分支意味着变更已满足团队约定。直接把未完成代码推到主分支，可能破坏其他成员正在使用的版本；长期分支又容易偏离最新接口。

五人团队可以使用简单流程：Issue → 接口确认 → 短分支实现 → PR → 测试与审查 → 合并 → 更新状态。涉及 Agent 行为、金融指标、数据结构或前后端对接的工作，应在并行实现前先确认契约。

### 结果与操作

1. **准备仓库**：由 `[成员1或仓库维护者]` 创建 `[仓库名]`，加入团队成员，配置 `README`、`.gitignore`、Issue 模板和 PR 模板。
2. **保护主分支**：将 `main` 设为稳定集成分支；要求通过 Pull Request 合并，并运行基础自动检查。不要让每个人直接向 `main` 推送未审查的功能。
3. **创建 Issue**：每项工作写明用户/业务问题、要实现的行为、输入输出、依赖模块、Owner、Shadow、验收条件和测试办法。
4. **先对契约**：需要多个模块协作时，先确认函数参数、API 请求与响应、数据字段、错误情况及权限边界。契约尚未决定时，先用示例数据或模拟响应推进，不要让不同成员猜接口。
5. **创建短分支**：例如 `feature/agent-tools`、`feature/cashflow-chart`、`feature/rag-evaluation`。一个分支尽量只解决一个 Issue。
6. **实现并自测**：提交前确认变更只涉及当前任务，运行对应测试，并检查没有密钥、个人数据或无关文件。
7. **发起 PR**：关联 Issue，说明改动目的、实现方案、测试结果、接口/数据变化和未解决问题；需要演示时附上不含敏感数据的截图或录屏说明。
8. **审查与合并**：由 Shadow 或其他成员检查需求、契约、异常情况和可维护性；CI 通过、反馈处理完成后再合并。
9. **同步与关闭**：合并后更新 Issue，删除完成分支，并从最新 `main` 开始下一项工作。

PR 描述可按此结构填写：

- 背景与目标：`[它解决的用户问题]`
- 变更内容：`[实现了什么，影响哪些模块]`
- 接口/数据变化：`[字段、函数、API 或契约变化]`
- 验证方式：`[运行了哪些测试/如何复现]`
- 风险与限制：`[未覆盖场景、模拟数据说明、权限影响]`
- 关联 Issue：`[Issue 编号或链接]`

## 5. 功能从业务问题到验收的闭环

### 原理与取舍

FinTechathon 项目不能只展示“Agent 调用了工具”，还要说明它解决了什么金融业务问题，以及结果是否符合金融逻辑。第四部分提出的工作闭环是 **Business → Agent → Quant → Engineering → Evaluation**。顺序很重要：若先写代码再寻找业务价值，团队可能做出能运行但无法解释的功能；若先定金融指标但不设计测试，就难以知道实现正确与否。

同一项功能需要业务视角、Agent 行为、金融计算、软件接口和评估标准共同定义。成员可以有主责，但不能把其中一个环节完全排除在讨论之外。

### 结果与操作

以“用户想知道为什么储蓄率下降”为例，每个功能先回答：

1. **Business Problem**：用户遇到什么问题？例如 `[用户不知道过去六个月储蓄率下降的原因]`。
2. **User Need**：用户最终需要什么结果？例如 `[看懂变化、知道主要支出类别并获得可解释建议]`。
3. **Agent Task**：Agent 要理解什么意图、需要哪些数据、何时向用户追问？
4. **Financial Logic**：指标如何定义？例如先由 `[成员1]` 确认收入与支出定义及边界，再由 `[成员3]` 实现 `SavingRate = (Income - Expense) / Income`，并明确收入为零或数据缺失时的处理方式。
5. **Tool**：Agent 通过什么接口获得数据或计算？例如 `[成员2]` 实现 `analyze_cashflow()`，明确输入字段、期间、币种和返回结构。
6. **Engineering**：哪个模块负责数据清洗、计算、模型解释、界面展示和错误处理？各模块通过哪些接口连接？
7. **Evaluation**：用哪些案例验证答案、计算、依据和安全行为？例如准备 `[测试账户数据]`，给出预期值，并检查 Agent 是否错误访问其他用户数据。

将以上内容写进 Issue 或功能设计页。需求、指标、工具参数或验收行为变化时，先更新契约，再更新实现和测试。

## 6. 五周开发顺序与每周交付

### 原理与取舍

团队同时从零学习 Python、机器学习、React、Agent 框架和向量数据库，容易出现每个人都学了一点，但没有可运行成果。分阶段开发能够尽早获得最小 Agent，再逐步扩展 RAG、Dashboard、安全和完整 Demo。周数是参考节奏，不应凌驾于真实比赛日期；如果赛程少于五周，Risk/Security 必须提前并行，不能因为时间紧而推迟安全验证。

开发顺序也体现依赖关系：先统一业务、数据 Schema 和 Agent Workflow；再打通模型、工具与计算；之后接入 RAG 和界面；再加强风险与安全；最终只保留少数完整且可靠的演示旅程。

### 结果与操作

#### Week 1：所有成员先理解同一个项目

五人共同完成 Business Problem、Use Cases、System Architecture、Data Schema 和 Agent Workflow。用一次团队评审确认核心用户旅程、数据来源、金融指标定义、工具接口草案和主线 Demo。不急着分别开发完整 UI 或复杂技术模块。

**本周交付：**项目目标和非目标、模块图/文字数据流、首版数据 Schema、Issue 清单、角色 Owner+Shadow 表、最小验收标准。

#### Week 2：做最小 Agent

只实现一条最小可运行链路：`User → LLM → Tool → Financial Calculation → Answer`。例如用户询问消费，Agent 调用 `get_transactions()`，再运行确定性支出计算并返回结果。工具可以先使用固定的合成样例数据。

**本周交付：**可运行的最小 Agent、至少一个工具、一个金融计算函数、自动化单元测试和启动说明。

#### Week 3：加入 RAG 与 Dashboard

在已经跑通的核心链路上添加获准金融文档检索和来源展示，同时由前端成员完成简单 Dashboard、Chat Interface 与必要图表。避免为第一版同时引入多个 UI 库或复杂前端框架。

**本周交付：**可展示的聊天/仪表板、一个 RAG 查询路径、答案来源或依据展示、基础集成测试。

#### Week 4：完善 Risk / Security

加入权限校验、Prompt Injection 相关测试、Risk Check、用户确认和 Audit Log。若实际比赛周期少于五周，至少应从 Week 1 同步讨论风险边界，并在 Week 2 的最小链路中加入基础权限检查，而不是把所有安全工作留到最后。

**本周交付：**风险场景清单、权限与确认规则、拒绝路径测试、关键 Agent 事件审计记录。

#### Week 5：完成端到端 Demo

聚焦 `[1-2 个]` 最完整业务场景，对全链路进行排练、测试和修复。准备备用演示数据与失败时的解释方案，确保演示结果可重复，而不是依赖临场手动修改数据。

**本周交付：**端到端验收结果、固定 Demo 脚本、已知限制、更新后的文档和答辩分工。

## 7. 技术栈收敛与 Demo 策略

### 原理与取舍

技术栈越多，安装、接口、调试和部署问题越多。五人学生团队应优先选择容易共同运行、容易演示和团队至少有人熟悉的方案。架构第四部分建议围绕 LLM、Agent、Python、FastAPI、PostgreSQL/SQLite、RAG/Vector DB 与 React 建立简洁主线；Quant 可使用 NumPy、Pandas、SciPy，图表使用 React 加图表库。具体组合仍须由团队按经验和时间确认。

Multi-Agent、Knowledge Graph、Graph Database、Kubernetes、微服务、Kafka、Redis 和复杂云架构都可能在特定规模下有价值，但它们不是默认的比赛加分项。没有明确需求时，增加这些组件更可能扩大集成风险，挤占业务闭环和验收时间。

### 结果与操作

1. 在 Week 1 决定首版最低可行技术栈，并固定语言/依赖版本。
2. 优先打通单体或简单模块化应用；只有当团队遇到可说明的扩展、隔离或部署问题时，才评估额外服务或基础设施。
3. 将 Demo 分为主线与支线：
   - **主线：个人金融 Agent**：`Analyze → Diagnose → Budget → Confirm → Monitor`，重点展示数据分析、预算建议、风险检查、用户确认和后续监控。
   - **支线：Financial Product Assistant**：`User Requirement → Product Search → Product Comparison → Risk Analysis → RAG → Explain`，只有主线稳定且时间允许时再加入。
4. 主线优先保证数据和计算可信、Agent 状态可见、审批行为明确、结果可复现。支线不得削弱主线测试或抢占最终集成时间。
5. 对每项新增技术提出问题：它解决当前哪个明确问题？团队是否能在截止前完成接入和测试？若答案不清楚，则暂缓采用。

## 8. 团队检查清单与常见偏差

### 原理与取舍

协作问题通常不是成员不努力，而是目标、接口和责任边界不清。以可观察的检查点审视工作，比只看提交数量或在线时间更有用。检查清单应帮助团队及早发现“模块做完却接不上”“大二变成单点故障”或“演示很漂亮但没有业务验证”等偏差。

### 结果与操作

每周例会或阶段复盘逐项确认：

- 每个功能都能说明对应的 Business Problem 和 User Need。
- 每个 Issue 有 Owner、Shadow、接口依赖和可验证的验收条件。
- 金融指标由负责成员共同明确定义，不是边写代码边猜公式。
- Agent、工具、数据、前端之间使用共同约定的字段和响应结构。
- 成员有持续交付，而不是所有代码、调试和 Demo 都集中在 Tech Lead。
- RAG 资料来源可追踪；评测包含正常问题、风险问题和越权问题。
- 安全、权限和审计不是最后一天才加入；任何写操作的批准边界清晰。
- 主线 Demo 能够端到端重复运行；支线功能不会妨碍核心验收。
- 引入新框架或基础设施时，有明确需求、负责人、集成计划和退出方案。

发现偏差后，把具体问题转成 Issue，明确修复负责人和期限。例如“成员5没有提交代码”应进一步确认是否因为任务定义不清、缺少样例资料、环境阻塞或评估方法不明确，再决定如何拆解和支持。

## 9. 结论与推荐

### 原理回顾

第四部分的核心不是把五个人机械地分成五块，而是由一名 Tech Lead/Agent Architect 保持系统整体连贯，同时让四名大一成员分别在 Agent/Backend、Financial Data & Quant、Frontend/Visualization、RAG/Research/Evaluation 上逐步承担更完整的责任。Owner + Shadow 让责任清楚又能共享知识；Business → Agent → Quant → Engineering → Evaluation 闭环确保技术功能对应实际业务问题；收敛技术栈和分阶段开发，则能降低集成与学习成本。

### 最后建议

建议团队先确认五个角色、首版业务场景和接口契约，再按 Issue 和短 PR 推进工作。让成员1负责架构与指导而非包办；让成员2从明确工具函数成长到 Agent/Backend；让成员3先做好数据清洗和基础指标，再扩展 Quant；让成员4通过 Dashboard 和 Agent 状态展示获得快速反馈；让成员5从研究、RAG 和测试集成长为 Evaluation 负责人。每周检查主线是否可运行，并根据真实赛程调整阶段，不以堆技术名词替代交付。

**为什么采用这种合作架构？** 因为它同时解决了五人团队的两类风险：一是系统缺少整体设计，模块无法集成；二是只有一名成员掌握关键知识，其他成员难以成长或接手。由 Tech Lead 保障系统连贯、由各模块 Owner 负责交付、由 Shadow 分享关键知识，再用 GitHub Issue/PR 和业务验收将合作过程可见化，能让团队既保持推进速度，也避免单点依赖。推荐把它作为默认起点，并依成员能力与项目周期灵活调整具体工作量。
