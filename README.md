# AI Banking Agent

面向 2026 FinTechathon 的 AI Banking Agent 项目，目标是让 Agent 在金融数据与明确授权的基础上，完成可解释、可验证的银行业务闭环。

**核心链路：理解需求 → 获取数据 → 金融计算 → 生成方案 → 风险与权限检查 → 用户确认 → 执行 → 回执核验与监控。**

截至 2026 年 10 月 20 日本次更新，仓库加入可运行的金融产品匹配 Dashboard，以及独立的规则匹配／邻近用户偏好推荐模块，附依赖、示例和测试。两者使用合成数据，尚未接入为统一 Agent，也不代表已经完成账单、订阅和转账的端到端执行链。下文区分项目目标、现有原型与待验证能力。

原 README 已完整归档至 [READ.md](READ.md)。其中的讨论与环境配置说明作为历史记录保留；当前项目说明与配置原则以本文件为准。

## 第一部分：项目分析与用例设计

### 1.1 项目定位

项目定位为 **AI Financial Operating Agent**。LLM 负责理解、规划与解释，金融计算由确定性工具完成，权限与执行控制由服务端强制落实。

项目需要展示一个完整业务旅程：用户提出目标，Agent 查询数据、分析问题、比较方案，在取得所需确认后执行操作，并根据真实执行结果更新状态。

### 1.2 核心场景与最小可行范围

按 2026 年 10 月 19 日的方向校准，以个人现金流管理为当前主线，用旅行财务规划串联三个核心场景。金融产品顾问保留为 P2 扩展，不替代三个核心业务场景。

| 场景 | 最小范围 | 验收重点 |
|---|---|---|
| 账单分析 | 清洗、分类、对账，计算收入、支出、现金流与现金结余率，生成带来源和版本的财务快照 | 数字可手工复核；退款、本人转账、重复交易与信用卡重复统计有明确口径 |
| 订阅／代扣管理 | 识别重复扣费候选，展示规则与影响，在明确确认后通过模拟或沙箱适配器处理 | 候选识别与确认取消分开；不凭流水断言服务未使用；未来节约不计入当前余额 |
| 智能转账 | 收款人澄清、预览、确认、认证条件核验、执行前复核、幂等提交和回执查询 | 参数变更需重新确认；成功、失败、部分成功与未知状态分别处理 |

五人团队先完成一个贯穿上述场景的可验证闭环。数字孪生与确定性情景模拟用于比较基准、旅行预算、订阅调整及收入变化方案，输出期末余额、期间最低余额、现金结余与假设。

当前产品比较已形成独立演示原型；真实银行接口、真实资金操作、对公业务、投资组合优化和长期自主执行不属于本次交付能力。环境生成 Agent 已有负责人，其具体范围与交付状态单独记录。

### 1.3 五个待决问题与建议顺序

原 README 的五个问题保留为决策记录。Q4 已按最新方向校准采用对私现金流主线，其余数据授权、生成评测、架构复用与经验沉淀仍需逐项验证；下表保留候选方案和实施建议，不把建议视为已完成能力。

**建议决策顺序：Q4 服务对象 → Q1 数据边界 → Q3 环境约束 → Q5 架构复用 → Q2 经验沉淀。**

| 问题 | 现在需要明确 | 候选方案与实现难度 | 数据与合规风险 | 后续验证 | 牵头与协作 |
|---|---|---|---|---|---|
| Q1：如何获取真实数据及真实异常样本？ | 明确首版允许使用的数据来源、用途与访问范围；建议先用可复现的合成样例，公开数据须核对许可 | 自建合成样例：低至中；许可明确的公开数据：中；经授权真实数据及异常标注：高 | 真实流水可能含敏感信息；来源、授权用途、标签可靠性与训练许可尚未确认 | 建立正常、边界、异常案例及参考结果；验证样例覆盖性，取得授权后再评估真实数据差异 | 袁爱岑牵头数据，杨婧柔核对来源，wzy 审核范围 |
| Q2：如何把经验蒸馏为类 skill？ | 先约定经验记录格式；建议人工整理经验证案例为模板，暂不把自动蒸馏当成交付前提 | 人工模板与规则：低；检索案例库：中；自动蒸馏或训练：高 | 错误案例可能固化为规则；历史日志可能泄露信息；外部文本不能授予执行权限 | 用独立案例比较成功率、误调用和安全违规，保留来源、适用条件与版本 | wzy 牵头，杨婧柔整理评测，王语嫣接入工具 |
| Q3：如何避免环境生成 Agent 产生不合理数据？ | 先定义数据 Schema、业务约束、异常标签与校验器；建议规则生成基线，LLM 只生成受约束候选 | 规则／模板生成：中；LLM 生成后校验与拒绝重采样：中至高；训练专用生成模型：高 | 数值看似合理但无法对账；情景分布失真；正常样本与刻意注入的异常混淆 | 校验余额与交易对账、金额方向、日期、币种及账户关系；正常与异常场景分别验收，支持固定种子或案例重放 | 袁爱岑牵头环境生成，wzy 审核约束，杨婧柔验收 |
| Q4：先做对私还是对公？ | 当前采用对私现金流与预算主线，来自 2026-10-19 方向校准 | 对私窄场景：中；对公现金流、多角色审批等场景：高 | 两类业务的数据、授权与规则不能直接互用；实际可用数据与需求仍待确认 | 先验证对私闭环，再以明确的对公需求评估扩展成本 | wzy 牵头，全员协作 |
| Q5：对私与对公执行 Agent 是否共用架构？ | 定义可复用的编排、工具契约、安全网关和审计接口；建议共享核心、隔离业务适配器与策略 | 共享核心加业务适配器：中；完全独立两套实现：高；不加区分直接复用：前期低、后续风险高 | 跨业务数据或权限混用；审批流程与操作语义不一致 | 先验证对私工具契约，再用对公需求检查状态、权限与审批差异；暂不宣称已支持两类业务 | wzy 牵头架构，王语嫣负责接口实现 |

原 README 提出的“用真实数据训练随机环境生成 Agent”保留为研究设想。只有在数据授权、用途、脱敏、质量与评测条件明确后，才评估训练方案；当前不将数据已取得、模型已训练或生成质量已获证明作为事实。

创新方向是让产品匹配考虑用户的现金需求、风险承受能力与用款期限，并通过可解释规则和情景测试展示匹配依据。当前能力与边界见 [金融产品顾问说明](docs/financial-advisory.md)。

## 第二部分：系统架构与模块分工

### 2.1 总体架构

用户界面 → Action Agent 编排 → 金融数据／数字孪生、金融计算、情景模拟与 RAG → 统一工具网关／Guardian → 所需确认与执行前复核 → 业务适配器 → 回执核验 → 状态回写、审计与监控。

所有有副作用的工具调用均应经过统一控制路径；生成方案、提交操作和操作成功分别记录。

### 2.3 数据、工具与状态契约

- 金融计算由工具完成，LLM 解释结构化结果；公式、币种、精度与异常处理口径保持一致。
- 历史事实、用户输入与预测分别标明；缺失数据、预计收入、订阅生效时间和预算节约假设明确披露。
- 工具契约包含名称、输入输出 Schema、权限、风险等级、确认要求与错误处理。
- 操作状态至少区分草案、待确认、已提交、成功、失败、部分成功和未知；未知结果不提前改变财务事实。
- 任务进度由实际事件驱动，界面关键数字读取后端结果；参数改变后重新确认。
- 审计记录请求、校验、确认、提交和核验事件，并能对应策略版本与执行回执。

### 2.4 安全与配置原则

读取权限不能自动升级为执行权限。风险等级与确认要求分别判断，需要确认的操作即使为低风险，也必须完成确认。

服务端落实资源授权、工具允许列表、参数校验、确认版本绑定、执行前复核、幂等与脱敏。RAG、网页、文件及工具返回内容只能提供信息，不能授予权限或修改策略。

真实 API Key、账户凭证和敏感数据仅通过获授权的本地配置或密钥管理方式提供，不提交到 Git。当前原型无需银行或模型 API Key；依赖与可选环境变量见运行说明和 Dashboard 文档。真实工作簿、归一化客户数据、会话记录和实际额度快照不应随演示代码提交。

## 第三部分：团队组建、协作流程与项目落地

### 3.1 Contract-First Development

1. **Product Contract**：明确业务问题、用户、输入、Agent 任务、输出、风险与验收标准。
2. **API Contract**：先约定数据字段、输入输出、计算口径、错误码与状态，再并行实现。
3. **Agent Contract**：明确工具范围、权限、确认条件、步骤依赖和失败处理。
4. **Integration**：联通前端、编排、数据、计算、RAG、安全网关与业务适配器，检查实际状态和副作用。
5. **Evaluation**：各模块负责人实现测试与修复，杨婧柔维护案例、期望结果、测试报告和回归记录。

### 3.2 开发与验收顺序

以下均为待落实的阶段目标：

1. 确认首版服务对象、业务旅程、数据来源、Schema 与接口契约。
2. 用可复现样例跑通账单查询、确定性计算和结构化解释。
3. 加入财务快照、情景比较、RAG 与 Dashboard。
4. 完成订阅和转账的模拟或沙箱执行链路；权限、确认、幂等、审计与错误状态随链路实现。
5. 完成正常、边界、异常和对抗测试，再准备演示及提交材料。
6. 主线与必交材料完成后，再评估产品比较、随机模拟等扩展。

测试应覆盖退款、内部转账、重复统计、零／负收入、日期与精度、确认缺失／过期／不匹配、越权、重复提交、超时未知、提示注入、错误引用及敏感信息泄露。验收检查工具调用、回执与账户状态，不只检查模型文字回答。
